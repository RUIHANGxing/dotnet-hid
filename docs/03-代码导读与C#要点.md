## 2. C# 语法速查（只讲本项目用到的）

| 你在代码里看到的 | 叫什么 | 一句话解释 |
|---|---|---|
| `namespace TouchProbe.Hid` | 命名空间 | 给代码分组，避免重名 |
| `using System;` | using 指令 | 引入别的命名空间（不是"释放资源"的那个 using） |
| `internal static class Program` | 静态类 | 不能被 new，只能直接用类名调用 |
| `public sealed class HidDevice` | 密封类 | 不能被继承（作者明确表示"不要继承我"） |
| `public string DevicePath { get; set; }` | 属性 | 看起来像字段，实际是 get/set 方法（可以加逻辑） |
| `private IntPtr _handle;` | 字段 | 类里的变量（下划线开头是常见命名习惯） |
| `out bool readAccess` | out 参数 | 方法通过它"带回"一个值（调用前不用赋值） |
| `ref HIDP_CAPS caps` | ref 参数 | 传引用进去，方法里改了外面也能看到 |
| `List<string> rows = new List<string>()` | 泛型集合 | 可变长数组，`<string>` 表示装字符串 |
| `devices.Where(d => ...).FirstOrDefault()` | LINQ | 用一行话筛选/排序集合，`=>` 是 lambda（匿名函数） |
| `using (HidDevice device = HidDevice.Open(info)) { ... }` | using 语句 | 代码块结束时自动调用 `device.Dispose()`，释放句柄 |
| `Console.CancelKeyPress += (s, e) => { ... }` | 事件 + lambda | 注册"按 Ctrl+C 时干什么" |
| `async Task<int> Main` / `await foreach` | 异步编程 | 见第 5 节（这是本项目给你的重点作业） |
| `(double X, double Y)` | 元组 | 把几个值临时打包在一起 |
| `?.` / `??` | 空合并/空条件 | `a?.b` 表示 a 为 null 就不访问；`a ?? b` 表示 a 为 null 就用 b |

**两个最容易混的点：**

1. `using System;`（文件开头）和 `using (var x = ...) { }`（代码块）是**完全不同**的两件事，
   前者是"引命名空间"，后者是"用完自动释放"。
2. C# 里的 `bool` 在内存里默认占 4 字节（Win32 的 BOOL），而 HID 结构体里是 1 字节的 BOOLEAN，
   所以声明时要写 `[MarshalAs(UnmanagedType.U1)]`（U1 = 1 字节无符号）。写错会导致整个结构体错位。

## 3. P/Invoke 与内存：C# 怎么调用 C 写的 Windows API

### 3.1 声明（DllImport）

```csharp
[DllImport("hid.dll", SetLastError = true)]
[return: MarshalAs(UnmanagedType.U1)]
public static extern bool HidD_GetPreparsedData(IntPtr hidDeviceObject, out IntPtr preparsedData);
```

- `DllImport("hid.dll")`：去这个 DLL 里找函数（`SetLastError = true` 表示"失败时可以问系统要错误码"）。
- `extern`：没有方法体，实现由 DLL 提供。
- 参数类型要**一一对应**：C 的 `HANDLE` → C# 的 `IntPtr`，C 的 `PHIDP_PREPARSED_DATA*` → `out IntPtr`。
- `[return: MarshalAs(UnmanagedType.U1)]`：C 的 `BOOLEAN` 是 1 字节，C# 的 `bool` 默认按 4 字节编组，
  必须显式声明，否则返回值可能读错。

### 3.2 结构体布局

```csharp
[StructLayout(LayoutKind.Sequential)]
public struct HIDP_CAPS
{
    public ushort Usage;
    ...
    [MarshalAs(UnmanagedType.ByValArray, SizeConst = 17)]
    public ushort[] Reserved;      // C 里的 USHORT Reserved[17]
}
```

- `LayoutKind.Sequential`：字段按声明顺序排列，和 C 一致。
- 数组字段要用 `ByValArray + SizeConst` 声明"内联数组"（不是指针）。
- **布局必须和系统里真实的结构体一模一样**，错一个字节，后面全部错位。

### 3.3 非托管内存（HeapAlloc 那一类）

```csharp
IntPtr buffer = Marshal.AllocHGlobal((int)requiredSize);   // 分配
try { ... } finally { Marshal.FreeHGlobal(buffer); }       // 必须释放
```

C# 的垃圾回收**管不到** `AllocHGlobal` 分配的内存，也不管 `HidD_GetPreparsedData` 返回的内存，
所以这些都要手动释放。本项目把"释放"集中在 `Dispose()` 里，配合 `using` 使用，避免漏掉。

### 3.4 ★结构体标定：本项目踩过的最狠的坑

**现象**：`caps` 命令跑到一半，程序直接崩溃，退出码 `0xC0000374`（堆损坏），没有任何异常提示。

**原因**：网上很多 C# 示例把 `HIDP_BUTTON_CAPS` 声明为 52 字节（保留区 18 字节），
而本机（Windows 26100）实测真实结构体是 **72 字节**。
于是系统往我们的数组里写 11 × 72 字节，我们只准备了 11 × 52 字节 —— 多出来的数据把堆踩坏了。

**怎么标定（这套方法可以复用到任何"不确定布局"的结构体）**：

```csharp
// 1) 用 byte[] 当缓冲区调用原生函数（不让 C# 做结构体编组，纯拿原始字节）
byte[] buffer = new byte[16384];
ushort len = caps.NumberInputButtonCaps;
HidP_GetButtonCaps(0, buffer, ref len, preparsedData);

// 2) 找"步长"：真实结构体大小 = 相邻两条记录在内存里的间隔
//    做法：假设一个 stride，看 buffer[i] == buffer[i+stride] 的比例有多高
//    匹配率接近 1 的那个 stride 就是真身（实测得到 72）

// 3) 再按 ushort 打印第一条记录的每个偏移量，和字段语义对照
//    例如偏移 56 处出现 0x42（Digitizer/Tip Switch）→ 联合体在 +56
```

标定结果直接写进了代码（`NativeMethods.cs` 里带 `// +0 +2 +4` 这类偏移注释），
并加了运行时自检：`EnsureStructSize(...)` —— 大小对不上就报错，而不是让程序莫名其妙崩溃。

## 4. 位运算：报告解码的全部秘密

HID 报告是连续的位流，取第 `offset` 位开始的 `size` 位：

```csharp
public static ulong ExtractBits(byte[] data, int dataStartByte, int bitOffset, int bitSize)
{
    ulong result = 0;
    for (int i = 0; i < bitSize; i++)
    {
        int bitIndex = bitOffset + i;          // 这是整个报告里的第几位
        int byteIndex = dataStartByte + bitIndex / 8;   // 落在第几个字节
        int bitInByte = bitIndex % 8;                   // 该字节里的第几位
        ulong bit = (ulong)((data[byteIndex] >> bitInByte) & 0x01);
        result |= bit << i;                    // 放到结果的第 i 位
    }
    return result;
}
```

三个必须知道的位运算：

| 运算 | 写法 | 用途 |
|---|---|---|
| 取某一位 | `(b >> n) & 1` | 右移 n 位，把目标位挪到最低位，再和 1 做"与" |
| 清零/保留某些位 | `x & mask` | 只想保留低 4 位就 `x & 0x0F` |
| 拼装 | `x \|= bit << n` | 把 bit 放到第 n 位 |

**有符号数（补码）**：如果描述符里"逻辑最小值 < 0"，这个字段就是有符号的。
最高位是 1 表示负数，值是 `原始值 - 2^位数`：

```csharp
if ((raw & signBit) != 0) value = (long)(raw - (1UL << bitSize));   // 例如 0x81（8位）→ -127
```

## 5. ★Task 与异步：本项目给你的主线作业

导师让你学 Task，而"读设备 → 处理 → 显示"正好是最典型的异步场景。项目里**同一件事写了两遍**，
就是让你对照着体会：

| | 同步版 | 异步版 |
|---|---|---|
| 入口 | `Program.RunWatchLoop` | `Program.RunWatchLoopAsync` |
| 取数据 | `while(true) { ReadInputReport(); }` 阻塞主线程 | `Task.Run` 里阻塞，主线程用 `await foreach` 消费 |
| 跨线程传数据 | 不用（都在一个线程） | `Channel<byte[]>`（有界队列，满了丢最旧） |
| 停止 | Ctrl+C 直接 `Environment.Exit` | `CancellationTokenSource` → 优雅收尾 |
| 好处 | 好懂，适合第一次读 | 界面不卡；采集与显示解耦；可以放心加处理逻辑 |

### 5.1 生产者-消费者（`Hid/ReportPipeline.cs`）

```csharp
// 生产者：后台线程里跑阻塞式读取，读到就丢进传送带
Task.Run(async () => {
    while (!token.IsCancellationRequested) {
        byte[] report = device.ReadInputReport();          // 阻塞在这里没关系，反正是后台线程
        await channel.Writer.WriteAsync(report, token);
    }
});

// 消费者（主流程）：一条条取出来处理
await foreach (byte[] report in channel.Reader.ReadAllAsync(token)) {
    ... 解码、显示 ...
}
```

### 5.2 几个真实的知识点（都在代码注释里标了位置）

1. **`Task.Run` 不等于"变快"**：它只是把等待挪到别的线程，让主线程不被堵住。
2. **有界 Channel 的背压**：`BoundedChannelOptions(256) { FullMode = DropOldest }` ——
   收集速度可能远超显示速度（触摸板一秒上百包），有界队列保证内存不爆，代价是会丢旧数据。
   程序退出时会打印"生产多少包 / 消费多少包"，数字不一样就说明丢过数据。
3. **取消不是万能的**：`ReadFile` 阻塞在后台线程里，`CancellationToken` 叫不醒它。
   所以 `StopAsync` 用 `Task.WhenAny(producer, Task.Delay(500))` —— 等一会儿就走，不做无限等待。
   想让 IO 真正可取消，要用重叠 IO（Overlapped）或超时机制。
4. **多线程计数要用 `Interlocked`**：普通的 `count++` 在多线程下会丢数。
5. **窗口消息必须由创建窗口的线程收**：Raw Input 的接收器只能在生产者任务**内部**创建
   （见 `ReportPipeline.StartForRawInput` 的注释）—— 这是 Windows 消息机制的一条硬规则。
6. **异步里不要 `Thread.Sleep`**：要等等就用 `await Task.Delay(...)`（本项目为了简单，
   在 Raw Input 的等待循环里用了 `Thread.Sleep(20)` 并在注释里说明了原因：那里本来就是个轮询循环）。

### 5.3 建议的练习顺序

1. 先跑 `watch --mouse --plain`（同步版，输出好读），确认能解出坐标/按键；
2. 再跑 `watch --mouse --async --plain`，对照两份代码找出"同一件事"的两种写法；
3. 给异步版加一个功能：**每 10 秒打印一次平均报告频率**
   （提示：用 `Stopwatch` + `Interlocked`，或者用 `System.Threading.Timer`）；
4. 把 `DropOldest` 改成 `Wait`，观察程序行为的变化（体会"背压"）；
5. 把 `--async` 的 `await foreach` 换成 `while + TryRead + await Task.Delay(10)`，
   比较两种写法的差别（`TryRead` 不等待、`ReadAllAsync` 会等待）。
6. 最后一个挑战：把显示搬到 WinForms/WPF，用 `IProgress<T>` 或 `Channel` 更新界面（这就是 M2）。

## 6. 怎么确认"我解出来的值是对的"

`watch --verify` 会把**我们自己按位算的值**和**系统 API（HidP_GetData）解出来的值**并排列出来：

```
数据序号  字段                                我们自己算   系统解码   对照
1         Generic Desktop/X                   1234         1234       一致
```

- 全部"一致" → 说明我们对描述符的理解和位运算都正确；
- 出现"不一致" → 通常说明描述符里有我们看不到的**填充位**（原因见 `docs/01` 第 4 节），
  程序会在启动时警告"报告实际 232 位，我们只知道 225 位"。
  此时显示会自动改用系统解码的值（`Program.EffectiveValue`），保证你仍然能看到正确的坐标。

**这就是"拿不到原始描述符"的真实代价**：不是不能干活，而是必须多一道交叉验证的保险。
