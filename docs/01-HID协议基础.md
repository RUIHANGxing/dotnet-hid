# 01 · HID 协议基础（以及 Windows 是怎么把它藏起来的）

> 目标读者：完全没接触过通信协议、C# 也刚上手的人。
> 读完这篇，你应该能回答三个问题：HID 是什么？数据长什么样？为什么有些东西我们看不到？

---

## 1. HID 是什么

HID = **H**uman **I**nterface **D**evice，人机接口设备。键盘、鼠标、触摸板、手柄、游戏摇杆都算。

它的核心思想只有一条：**设备自己描述自己**。

传统设备的做法是"每出一款新鼠标，就得写一个新驱动"。HID 换了一条路：

- 设备启动时，先交出一份"说明书"——**报告描述符（Report Descriptor）**；
- 说明书用一套通用语法描述："我每次上报 N 个字节，第 0~2 位是三个按键，第 3~7 位没用，
  接下来 3 个字节分别是 X 位移、Y 位移、滚轮，范围是 -127~127"；
- 系统读完说明书，就**通用地**知道怎么解析数据了，不需要为每款设备写驱动。

所以：**学 HID = 学这本说明书的语法 + 学数据怎么按说明书切片**。这个项目就是把这两件事都做一遍。

## 2. 数据长什么样

### 2.1 报告的三种类型

| 类型 | 方向 | 例子 |
|---|---|---|
| Input（输入报告） | 设备 → 电脑 | 手指坐标、按键状态 |
| Output（输出报告） | 电脑 → 设备 | 键盘指示灯、手柄震动 |
| Feature（功能报告） | 双向、按需读写 | 配置项，如"最多支持几个触点" |

### 2.2 报告是"位流"，不是"结构体"

这是最容易踩的坑：**报告里的字段不按字节对齐**。

例如描述符里写了"3 个 1 位的按键 + 5 位填充"，那么第 1 个字节的**位 0、1、2** 是按键，
**位 3~7** 是没用的填充位；下一个字段直接跟在后面（如果它也是 1 位宽，就接着占位）。

所以解码报告的正确姿势是：
1. 计算每个字段的**起始位**和**位宽**；
2. 从字节数组里把这段位抠出来（低位在前）；
3. 按描述符里声明的逻辑范围判断它是不是有符号数、要不要换算。

这三步在 `Hid/ReportLayout.cs` 里实现，是我们这个项目的核心。

### 2.3 报告 ID

如果一个设备有好几种报告（比如触摸板既要报"触点"又要报"按键"），
描述符里会给每种报告分配一个编号（Report ID）。此时**每个报告的第 1 个字节就是 ID**，
后面才是数据。

> 本机实测：这块触摸板只用了 **1 种**输入报告，ID 是 `4`。
> 所以每包 30 字节 = 1 字节 ID + 29 字节数据。

## 3. 描述符的语法（先看个印象，细节在 02 篇）

描述符是一串"指令"，每条指令叫一个 item，格式是：

```
┌─── 前缀 1 字节 ───┐┌── 数据 0/1/2/4 字节 ──┐
| tag(4) | type(2) | size(2) |  little-endian 数值 |
```

指令分三类：

- **Global（全局）**：设置一个状态，之后一直有效，直到被改写。例如 `Usage Page`、`Logical Minimum`、`Report Size`。
- **Local（局部）**：只对紧随其后的那条 Main 指令生效，用完清空。例如 `Usage`、`Usage Minimum/Maximum`。
- **Main（主）**：真正产生"字段"的指令：`Input`、`Output`、`Feature`、`Collection`、`End Collection`。

举个最小的例子（一行就是一条指令）：

```
05 01        Usage Page (Generic Desktop)   ← Global：后面说的用途都在 0x01 页
09 02        Usage (Mouse)                  ← Local：这个设备是鼠标
A1 01        Collection (Application)       ← Main：开始一个应用集合
09 01        Usage (Pointer)
A1 00        Collection (Physical)
05 09        Usage Page (Button)            ← 切页
19 01        Usage Minimum (1)
29 03        Usage Maximum (3)              ← 3 个按键
15 00        Logical Minimum (0)
25 01        Logical Maximum (1)
95 03        Report Count (3)
75 01        Report Size (1)                ← 每个按键占 1 位
81 02        Input (Data,Var,Abs)           ← Main：产出 3 位的输入字段
...
```

### "用途"（Usage）是什么

每个字段都要说明"我是干什么的"，用一个二元组表示：

```
用途页 Usage Page（大类）+ 用途 Usage（小类）
```

| 编码 | 含义 |
|---|---|
| `0x01 / 0x30` | 通用桌面 / X 轴 |
| `0x01 / 0x31` | 通用桌面 / Y 轴 |
| `0x0D / 0x05` | 数字化仪 / 触摸板（**本机触摸板的顶层用途**） |
| `0x0D / 0x22` | 数字化仪 / 手指（每个触点用一个逻辑集合表示） |
| `0x0D / 0x42` | 数字化仪 / 笔尖开关（手指是否按下） |
| `0x0D / 0x51` | 数字化仪 / 触点编号 |
| `0x0D / 0x54` | 数字化仪 / 当前触点数量 |

完整的用途表在 `Hid/HidUsageNames.cs`（只收录了常用部分，够读懂触摸板）。

### 集合（Collection）与"每个触点一个集合"

描述符用 `Collection` / `End Collection` 配对，形成一棵树。触摸板的典型结构：

```
[0] Touch Pad（应用集合，整块板子）
 ├── [1] Finger（逻辑集合）  ← 第 1 个触点：编号 / 是否按下 / X / Y
 ├── [2] Finger（逻辑集合）  ← 第 2 个触点
 ├── [3] Finger
 ├── [4] Finger
 └── [5] Finger
```

**这是理解触摸板数据的关键**：同一根手指的 X、Y、编号、按下状态，都在"同一个逻辑集合"里。
所以解码时我们按 `LinkCollection` 分组，一组就是一个触点（见 `Program.cs` 的 `ExtractContacts`）。

## 4. Windows 的软件栈：我们的代码站在哪一层

```
你的 C# 程序（本项目）
   │  ← 只能从这里往下看
   ├── hid.dll / setupapi.dll     设备枚举、能力查询（HidP_* 系列）
   ├── hidclass.sys               系统 HID 类驱动：解析描述符、管报告
   ├── hidi2c.sys                 传输驱动：把 HID 请求翻译成 I2C 读写   ← 看不到
   ├── I2C 控制器 + 总线（AMD I2C Controller，ACPI 设备 AMDI0010）      ← 看不到
   └── FocalTech FTCS0038 触摸板芯片（先天的 I2C 设备）                  ← 看不到
```

**结论一：这块触摸板确实跑在 I2C 上**，但那根总线在机器内部、开机就被 ACPI + `hidi2c.sys` 接管，
Windows 用户态**没有**任何接口能在上面发 I2C 事务（Linux 才有 `/dev/i2c-N`）。
所以：这块板子能把 HID 学到极致，学不到 I2C 的电气层。

**结论二（实测踩坑）：连原始描述符字节都拿不到。**

我们试过这些方法（都写进了 `docs/03`，你可以复现）：

| 尝试 | 结果 |
|---|---|
| `HidD_GetReportDescriptor` | hid.dll 里根本没这个函数（实测串搜确认） |
| `IOCTL_HID_GET_REPORT_DESCRIPTOR`（0x000B0007 等一串候选码） | 全部返回"功能无效"；扫描 4 种缓冲方式 × 256 个功能号后确认：**该设备的 IOCTL 面里没有它** |
| 换一台 USB HID 设备再试 | 同样没有 → 不是 I2C 特有问题，是 Windows 的设计 |
| 扫描设备的全部 IOCTL | 只找到"预解析数据"（`HidP KDR` 开头的一大坨），里面**不含**原始描述符字节 |

Windows 只把**解析后的结果**（能力表、字段表、集合树）交给用户态。
这也是为什么成熟的跨平台库 hidapi 在 Windows 上是"从解析结果**反推**一份描述符"，而不是直接读。

**结论三：触摸板被系统独占，`ReadFile` 也读不了。**

实测（`CreateFile` 三种权限都试了）：

| 设备 | 申请读权限 | 结果 |
|---|---|---|
| 普通 USB 鼠标集合 | `GENERIC_READ` | 成功 |
| 本机触摸板 | `GENERIC_READ` | **失败，错误码 32（共享冲突）** |
| 本机触摸板 | 无权限（0） | 成功，但只能做查询，`ReadFile` 会被拒（错误码 5） |

原因：精确式触摸板的驱动（PTP）以独占方式持有这个集合。
解决办法是走另一条正规通道 **Raw Input**：不是"你去读设备"，而是"向系统登记：这个设备有输入时，
请把原始报告投递给我"。拿到的是**同样的原始字节**，只是换了个方向。
实现见 `Hid/RawInputReader.cs`，`watch` 命令会自动选择通道并告诉你用的是哪条。

## 5. 我们实际能拿到的东西（也就够用了）

| 能拿到 | 用什么 | 在本项目里的位置 |
|---|---|---|
| 设备清单、设备路径、实例 ID | SetupAPI | `Hid/HidDeviceEnumerator.cs` |
| VID/PID、厂商名、产品名 | `HidD_*` | 同上 |
| 能力汇总（顶层用途、报告长度、字段个数） | `HidP_GetCaps` | `Hid/HidDevice.cs` |
| 字段清单（用途、位宽、逻辑范围、所属集合） | `HidP_GetButtonCaps` / `HidP_GetValueCaps` | `Hid/HidCaps.cs` |
| 集合树 | `HidP_GetLinkCollectionNodes` | 同上 |
| **原始报告字节** | ReadFile 或 Raw Input | `Hid/HidDevice.cs` / `Hid/RawInputReader.cs` |
| 系统替我们解码的结果（用来对照） | `HidP_GetData` | `Hid/HidCaps.cs` |

**关键点**：字段清单里没有"起始位"。起始位是我们自己算出来的：
把字段按"数据序号（DataIndex）"排序——数据序号就是字段在报告里的出场顺序——
然后从第 0 位开始，一个字段一个字段往后累加位宽。这就是 `Hid/ReportLayout.cs` 做的事。

> 如果描述符里有"填充位"（常量字段），系统不会告诉我们它的位置，
> 那么我们算出来的偏移就可能整体错位。程序会把这件事**明确提示**出来，
> 并且用 `HidP_GetData` 的结果做交叉验证：一致就说明我们算对了。
> 这是"拿不到原始描述符"带来的真实麻烦，也是很好的教学素材。

## 6. 术语表

| 词 | 含义 | 备注 |
|---|---|---|
| Report（报告） | 设备与主机之间传输的一包数据 | 一次触摸会上报很多包 |
| Report Descriptor | 描述"报告里每一位是什么"的说明书 | 由设备提供，Windows 存在内核里 |
| Usage Page / Usage | 用途页 / 用途 | 描述字段语义的编码 |
| Collection | 集合 | 描述符里的层级结构，触点就是逻辑集合 |
| Report ID | 报告编号 | 有它时，报告第 1 字节就是它 |
| Logical Min/Max | 逻辑范围 | 数字的取值区间，最小值 < 0 表示有符号 |
| Physical Min/Max | 物理范围 | 换算到物理量（本项目暂未使用） |
| Const（常量） | 填充位 | 没有语义，只是为了对齐 |
| PTP | Precision Touchpad，精确式触摸板 | Windows 对触摸板的规范，本机就是 |
| Raw Input | 原始输入 | 系统主动投递原始报告的机制 |
